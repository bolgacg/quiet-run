Before anything else

Five things to know

This page is about the pump pressure of a liquid chromatography run. Here is what that is, in five sentences, so nothing after this assumes you have seen one.

  1. Liquid chromatography (LC) pushes a dissolved sample through a thin packed tube, the column, so the peptides in it come out one after another into a mass spectrometer that weighs them. Evosep builds the instruments that do this step for proteomics.
  2. A pump drives the liquid at a set flow. The pressure it needs depends on the column and on the liquid's mix, which changes along the run (the gradient), so a healthy run has a pressure shape of its own. The 2018 paper that introduced the Evosep One recorded that shape for each of 1,500 runs to show the column stayed clean.
  3. Faults change the shape in different ways. A leak lowers it, a clog raises it, air in the pump makes it twitch, and a column that slowly fouls lifts it a little more every run, which I call drift.
  4. Some faults leave the pressure alone. If the control software hangs on a step, the pump keeps pumping, the heartbeat keeps arriving and the status says Running, but the method stops moving. I call that quiet, and catching it needs a check on progress, not on presence.
  5. Everything here is synthetic. The run length is a public method, 60 samples per day: a 21-minute gradient plus about 3 minutes between injections (Bache et al. 2018). The pressure shape, the noise and the faults are invented, and pressure is an index where 100 is the healthy average for the method.

Terms, in the order they appear
pressure index Pump pressure divided by the healthy average for the method, times 100. A leak that costs percent of pressure moves it from about 100 to about .
fixed limits One low and one high pressure value for the whole run. If the pressure stays past either for seconds, the alarm trips. They are set from healthy runs as tightly as those runs allow.
envelope What a healthy run of this method shows at each point of the method, learned from healthy runs. quiet-run compares the pressure with the envelope at the same point, not with one number for the whole run.
method clock How far through its method the instrument says it is. A healthy run's clock moves every second except for short planned pauses.
heartbeat A counter the instrument increments while it is alive. It proves presence, not progress.
time to flag Time from the moment the fault began to the first alarm. For drift it is counted in runs.
false alarm An alarm on a healthy run. The study has healthy runs to count them on.
setting How strict quiet-run's rules are. Relaxed, chosen and sensitive were fixed before the study first ran.

With those terms in hand, the next question is whether this problem belongs to Evosep's software team at all.

Their words

Why a run-health monitor, for this team

This section matters because the demo should answer a question Evosep is already asking, not one I made up. The software team's own advertisement names the work.

"Design and develop software solutions that support both current and next-generation Evosep technologies, including software for instrument control, internal production support systems etc." Evosep, Software Developer advertisement, October 2026
"... the freedom to explore modern approaches such as AI-assisted and agentic development." Same advertisement

People do read these traces. Bache et al. (2018) recorded the pressure profile of every run in a 1,500-run test and showed that profiles of adjacent runs were "virtually indistinguishable". A third-party tool on GitHub, jjjotto/EvoSep_Data_Traces, lets Eno users plot pressure, flow rate and pump speed from their run folders. quiet-run asks the question a person looking at those plots asks, during the run rather than after it: is this run still healthy, and if not, why?

How I built it

Rules and tests first, then the code

This section matters because the advertisement asks for AI-assisted and agentic development, and this is how I do it on real work.

  1. I do not write C# by hand. I direct coding agents: I set the rules and what each test must prove, and I read, run and debug the code they write.
  2. I wrote the rules first, in plain English, one per fault: what the pump would show, and what the reason should say to the person at the instrument. The quiet rule comes from my own monitoring work, where a recorder once wrote empty files for twenty hours while every presence check passed.
  3. For each rule I wrote down what a test must prove: the fault is flagged with the right name within a time limit, a healthy run stays OK, and the same run is not flagged when that rule is switched off. A test that passes without its rule proves nothing.
  4. Agents wrote the C# against those tests, and I read it. The tests caught two real problems during the build. A fast leak was first called AIR, because its ramp crossed the spike threshold several times; the AIR rule now ends a swing only when it falls back under half the threshold. A drift test claimed more than the design delivers once runs carry random offsets; it now tests a clean trend, and the noisy case is measured in the study instead.
  5. Each rule is one class behind one interface. The monitor asks LEAK, CLOG, AIR and QUIET in turn on every reading, and DRIFT after every run, so one rule can change without touching the others. Every time and duration comes from the readings' own timestamps. Tests feed the monitor jittered, lost and unevenly spaced readings, and the verdicts held on every run except for AIR, which changed in 1 of 20 runs because a short dip can lose the readings that show it.
  6. The three settings were fixed before the study first ran and have not changed since, so the numbers above are not tuned to themselves.

The tests are what make me trust it. They run on every push in GitHub Actions, which also rebuilds this page's data from the code and fails if it differs from what is published.
